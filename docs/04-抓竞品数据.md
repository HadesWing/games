# 04 · 抓竞品数据并分析

> 目标：**在写任何产品代码之前，先搞清楚这个玩法在真实房间里到底跑不跑得动。**

你要验证的核心假设只有一个：

> 有人愿意为了多猜几个词而送礼吗？送多少？什么时刻送？

这个假设只能靠真实数据回答。而抓 3 场数据的成本，远低于把整套变现功能做完再发现没人付费。

---

## 一、先做一次管线自检（5 分钟）

在碰真实数据之前，先把 `采集 → 落盘 → 报告` 跑通，避免采了半天发现分析器有 bug。

```bash
cd 弹幕猜词   # 换成你的实际目录
node tools/sample.mjs
node tools/analyze.mjs --out data/report-sample.md
```

会生成一份**合成数据**的报告。这份报告的数字没有任何意义（是随机的），但你应该能看到：

- 结论先说（几条带颜色的判断）
- 概览表
- 每分钟弹幕量的柱状图
- 字数分布、高频词 TOP 30
- 礼物与付费表

**看到这些就说明管线正常。** 打开 `data/report-sample.md` 看一眼格式对不对。

⚠️ `data/SAMPLE-*.jsonl` 是假的，别拿它当结论。正式分析前删掉。

## 二、选房间：这步决定数据有没有用

### 不要选的

| 类型 | 为什么不行 |
|---|---|
| 在线几十人 | 弹幕太稀，一局可能只有 5 条，看不出规律 |
| 在线 5 万+ 的头部 | 弹幕滚太快，你根本看不清谁在猜什么；而且他的玩法和你的起步阶段完全不同 |
| 刚开播 5 分钟 | 数据量不够，礼物还没起来 |
| 不是猜词玩法的房间 | 白采 |

### 要选的

**在线 500–5000 的中腰部、已经播了 30 分钟以上、明确在做猜词玩法**的房间。

这个区间最像你起步时的状态：有人看，但还没形成铁粉，观众行为最真实。

### 怎么找

在抖音搜「猜词」「弹幕猜词」「猜明星」这类关键词的直播，按在线人数筛。找到一个之后，看它的**观众互动质量**——有人真的在猜词、有人送礼，就对了。

## 三、采集

三种方式，按你手上有什么选。

### 方式 1：接代理类工具的 ws（最省事）

前提：已经按 `02-操作手册.md` 第 1.4 节把 `DouyinBarrageGrab` 跑起来了。

```bash
cd 弹幕猜词   # 换成你的实际目录
node tools/collect.mjs ws ws://127.0.0.1:8888 --room 745964462470
```

`--room` 只是用来命名文件，写个你认得出的标识就行。

会看到：

```
  采集目标：745964462470
  输出文件：data/745964462470-20261110-1502.jsonl

[15:02:11] 已连接 ws://127.0.0.1:8888
[15:02:21] 累计 186 条 · 聊天 142 · 礼物 3
```

**看到「累计」在涨就正常。** 这个方案能拿到完整礼物流，是**首选**。

### 方式 2：管道接 Python 工具的控制台输出

```bash
# 窗口 1
cd .../DouyinLiveWebFetcher
python main.py > danmu.log 2>&1

# 窗口 2
cd 弹幕猜词   # 换成你的实际目录
node tools/collect.mjs stdin --room 745964462470 < danmu.log
```

⚠️ 这种方式拿到的礼物**没有钻石金额**（Python 工具只打印礼物名），报告里的付费分析会不准。能用方式 1 就别用这个。

### 方式 3：先干跑确认字段对不对

第一次接新的抓取工具，先看一眼解析出来的东西对不对：

```bash
node tools/collect.mjs ws ws://127.0.0.1:8888 --room test
# 跑 1 分钟后 Ctrl+C，然后：
head -20 data/test-*.jsonl
```

正常应该是：

```json
{"t":1794292425928,"type":"chat","user":"小智","text":"纽扣"}
{"t":1794292426103,"type":"gift","user":"YY","gift":"小心心","count":10,"diamond":1}
{"t":1794292426588,"type":"like","user":"佩佩","count":9}
```

**如果 `user` 是空的、或 `text` 是乱码**：说明字段名不匹配。打开 `tools/collect.mjs` 的 `toEvent()`，把 `Nickname` / `Content` 这些键名改成你实际看到的（用 `--dry` 配合打印原始 JSON 排查）。

## 四、采多久

**一个房间至少连续采 1 小时**，最好覆盖完整的「开播 → 中段 → 下播前」。

理由：送礼是有节奏的。

- 开播前 15 分钟：老粉进场、打卡礼
- 中段：榜一榜二拉扯、连击
- 下播前 10 分钟：冲刺、告别礼

只采 20 分钟，你大概率只看到中段的低谷。

**推荐节奏：一个下午采 3 个房间，各 1 小时。** 三个样本才能看出「哪些是这个玩法共有的规律，哪些是这个主播的特质」。


报告会同时打印到终端并存成 md。

## 六、报告怎么读（重点）

别只看数字，每个指标对应一个具体决策：

| 指标 | 什么情况算异常 | 对应动作 |
|---|---|---|
| **弹幕密度** | < 5 条/分钟 | 房间太冷，样本作废，换房间 |
| **1–3 字占比** | < 30% | 观众不按规则玩。你的画面上要把「发 1–3 个字」做成更大的提示，否则大量有效猜测被浪费 |
| **重复率** | > 50% | 榜单必须按词去重。**本地原型已经做了**，这是为什么榜单看起来干净 |
| **Top10 用户占比** | > 50% | 参与高度集中。榜单要给这几个活跃用户专属标识（称号、连击特效），讨好他们比讨好所有人有效 |
| **礼物频次** | < 5 次/小时 | **这个房间不适合做付费玩法**，换样本。如果三个房间都低于这个数，整个赛道要重新评估 |
| **榜首占收入比** | > 50% | 收入结构很脆，榜一走了当晚归零。定价要围绕榜一设计，但同时要找中腰部付费理由 |
| **高频词 TOP 30** | —— | 这是**你词库的第一批素材**。反复出现却从没猜中的词，就是天然的干扰项 |

### 三个必须回答的问题

分析完，合上报告，只回答这三句：

1. **这个房间一局大概要多少条弹幕才能猜中？**（看弹幕密度 × 单局时长）
   → 决定你的倒计时设多长、免费次数给几次
2. **礼物集中在什么时刻？**（看每分钟柱状图 + 礼物分布）
   → 决定你的提示什么时候解锁、什么时候推「送个礼继续猜」
3. **观众最常猜的那 20 个词是什么？**
   → 直接抄进你的词库当干扰项，比自己想快 10 倍

## 七、合规边界（别越线）

采集是为了自己看规律，不是拿别人的数据做生意。三条底线：

- **只采公开弹幕**，不碰任何需要登录才能看到的内容
- **不存储、不整理、不外发**用户的可识别信息（昵称截断、不记录 uid、不做用户画像）
- **不批量、不长期挂机**。抓几个样本做判断，不是做数据库
- **不发到公开仓库**。`data/` 目录建议加进 `.gitignore`

如果这个项目以后要开源，`.gitignore` 里至少要有：

```
data/
node_modules/
```

## 八、做完这一步之后再决定什么

拿到三份报告，你会面临三种情况：

**A. 礼物频次健康（>10 次/小时）、集中度适中**
→ 玩法成立，值得做。继续按 `02-操作手册.md` 走阶段 2、3。

**B. 礼物频次健康，但榜首占 80% 以上**
→ 玩法成立但只有「榜一大哥」模式。你的产品要把榜一体验做到极致（专属特效、连麦、私信感谢），别指望长尾付费。

**C. 三个房间礼物频次都 < 5 次/小时**
→ **这个赛道的付费假设不成立。** 别做了，或者改成不带付费的涨粉玩法（用猜词做流量入口，靠带货变现）。

C 是最可能的结果，也是最省钱的结论。**花一个下午得到这个结论，比做完一套变现系统再发现要值一百倍。**
