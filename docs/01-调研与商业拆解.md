# 01 · 调研与商业拆解

> 调研时间：2026-11-10。抖音的接口和规则变化很快，本文的技术结论有时效性，动手前请先按 `02-操作手册.md` 做一次最小验证。

---

## 一、这个玩法是什么

主播给一个**目标词**（限定词性、字数、分类，例如「名词 · 1–3 字 · 服饰」），观众在弹幕里发词猜。系统对每个猜测实时算一个**关联度百分比**，越接近答案分越高；猜中即赢下这一局，然后换下一题。

关键点：**那个百分比不是对错判定，是语义距离**。

截图里的实测数据能印证这一点：

| 猜测 | 分数 | 说明 |
|---|---|---|
| 襟 | 89.8% | 单字，但极具体 |
| 衣襟 | 86.9% | 同义/近义 |
| 襟花 | 84.8% | 共享罕见字 |
| 布扣 / 扣子 / 门扣 | 84.6 / 83.9 / 83.1 | 同属扣合件 |
| 纽扣 | 77.2% | 同一个东西的另一种叫法 |
| 衣 | 64.1% | 单字，但太泛 |
| 衬衫 / 领结 | 62.8 / 59.3 | 同分类、不同部件 |

注意两组对比：

- **「襟」89.8 vs「衣」64.1** —— 都是答案里的字，但「襟」罕见、「衣」常见。说明打分对**具体性**敏感。
- **「纽扣」77.2 反而低于「布扣」84.6** —— 说明它不是严格的同义词判定，更像「在某个语义空间里的远近」。

这两条观察直接决定了自建版的算法设计，见 `03-关联度算法.md`。

## 二、钱从哪来

截图右侧的几个栏位已经把商业模式写全了。逐项对应：

### 1. 送礼换猜测次数

右侧「随机词」栏：

```
点赞        1 词
（某礼物）   50 词
（某礼物）   600 词
```

这是最核心的变现点。免费用户每局能猜的次数有限，送礼解锁更多。本质是**卖「参与感」**——猜词这件事，猜得越多越容易中，所以次数天然是刚需。

### 2. 送礼换提示

截图里「提示 1/3 已解锁 · 00:35 后第 2 条」，以及「魔镜 500 币/局」。

提示有两种解锁方式：**等时间**（免费但慢）或**花钱立刻看**。这是第二个变现点，比卖次数更暴利——因为提示一旦看到，中奖概率是线性提升的。

### 3. 关注换次数

「关注 600 词 + 限一次」。纯涨粉钩子，不直接产生收入，但**粉丝数决定了下一场直播的初始流量**，是复利项。

### 4. 榜一大哥经济

右侧「直播间榜」：小智 18 万、YY 9.9 万、墨个镜 7.8 万……

按平台通行的换算（1 元 = 10 音浪充值，主播提现约 50%）估算：

```
1 万音浪 ≈ 500 元 到主播（税前，未计公会抽成）
榜一 18 万音浪 ≈ 9000 元
```

再扣公会抽成（通常 20–30%），实际到手约 6000–7000 元。**这是一场的收入**，不是累计。

⚠️ 分成比例平台会调整，以上只用于判断量级，不要拿去当财务预测。

### 5. 流量 → 后端（真正的大头）

人气起来后：平台会推流 → 接带货、广告、私域导流、卖课。

**这一条才是天花板。** 前面四条加起来是「能养活自己」，第五条才是「能赚钱」。

### 6. 卖工具 / 收徒（另一门生意）

市面上大量这类直播间，主播本身就是在卖这套工具或卖课。这是**To B 而不是 To C** 的生意，判断逻辑完全不同（见第四节）。

## 三、技术路线：四条路，选哪条

「怎么拿到弹幕」是这个项目唯一真正的门槛。四条路：

| 路线 | 原理 | 延迟 | 完整性 | 维护成本 | 风险 |
|---|---|---|---|---|---|
| **A. 开源库直连 wss** | Python/Go 直接连抖音推送服务，自己算 signature | <1s | 全量 | 中（签名算法会变） | 中，需跟上游更新 |
| **B. 系统代理抓包** | 本地起代理，劫持浏览器/直播伴侣的 wss 流量 | <1s | 全量 | 低 | 中，需装证书+管理员 |
| **C. 浏览器 CDP 注入** | 附加到真 Chrome，hook `WebSocket.prototype` | <1s | 全量 | 中（页面改版要改解析） | 低，指纹真实 |
| **D. OCR 截屏** | 截手机/采集卡画面，识别聊天区文字 | 1–2s | **会漏** | 低 | 低 |

### 为什么直接排除 D（OCR）

不是识别不准，是**采样率**的物理限制：

聊天区只保留最近 N 条。你每 300ms 截一帧，这 300ms 内滚过去 20 条，你物理上只能拿到 5 条。把频率提到 50ms，OCR 引擎跟不上、CPU 打满、画面还卡。

**结果：高并发时必然大量漏，且漏的恰好是最活跃、最可能送礼的那批人。** 这是架构缺陷，优化不掉。

而且 OCR 认不出礼物名和连击数——而你变现全靠礼物。

### A 和 B 的区别，决定选哪个

- **B（代理）的优势**：能同时抓浏览器和**抖音直播伴侣**的流量。如果你用直播伴侣开播，这是最省事的。
- **B 的代价**：要装自签名证书、要管理员权限、系统全局走代理（可能影响别的软件）、代理挂了会影响上网。
- **A 的优势**：干净，不开代理，不影响系统。
- **A 的代价**：signature 算法在 `webmssdk.js` 里，会变；变了自己不会修就得等上游更新。

**建议：先用 A 跑通验证，跑通了再决定要不要换 B。**

## 四、现成开源项目（2026-11 调研）

> 这些仓库都不是官方 SDK，是社区逆向。抖音改协议就会失效。**用之前先在 issue 里看最近一次「测试成功」的时间。**

### 1. saermart/DouyinLiveWebFetcher —— 首选

- 地址：<https://github.com/saermart/DouyinLiveWebFetcher>
- 语言：Python 3.7+，附带 `douyin.proto`、`sign.js`、`a_bogus.js`、`webmssdk.js`
- 状态：README 里记录的最后成功测试是 **2026-08-26**，且有**编译好的 release 版本**（不用配 Python 环境）
- 输出：控制台打印 `【聊天msg】[uid]昵称: 内容`、`【礼物msg】xxx 送出了 yyy x1`

**这是调研到的维护最勤、文档最全的一个。** 它的 README 里有逐月记录测试成功的时间戳，这个习惯本身说明作者在持续跟。

### 2. Buterr04/DouyinDanmakuCatcher —— 想存数据选它

- 地址：<https://github.com/Buterr04/DouyinDanmakuCatcher>
- 基于上面那个改造，精简成单文件 CLI
- 特点：输出 **JSONL**（一行一条，时间戳毫秒归一化）、带**开播检测轮询**、支持礼物价值过滤
- 适合：先攒几天数据看真实弹幕长什么样

### 3. xiaoli9/DouyinBarrageGrab —— 走代理路线选它

- 地址：<https://github.com/xiaoli9/DouyinBarrageGrab>（主仓在 Gitee）
- 语言：C#，系统代理方案
- 特点：能抓**浏览器 / 抖音客户端 / 抖音直播伴侣**三种来源；本地起 ws 服务 `ws://127.0.0.1:8888`，其他程序接进去就行
- 注意：需要管理员权限 + 安装自签名证书；**必须先开程序再进直播间**，否则抓不到握手后的数据

### 4. douyin-live-go —— 想用 Go 选它

几百行 Go 跑通全流程，适合自己改。缺点是错误处理很粗（一次读失败直接 panic），长时间挂机要自己补重连。

## 五、协议长什么样（自己实现时需要）

三层解包：

```
WebSocket 二进制帧
  └─ PushFrame { seqId, logId, service, method, payloadType, payload }
       └─ payload 先 gzip 解压（payloadType 标记是否压缩）
            └─ Response { messagesList[], cursor, needAck, internalExt, pushServer }
                 └─ Message { method, payload }
                      ├─ method == "WebcastChatMessage"  → ChatMessage { user, content, rtfContent }
                      ├─ method == "WebcastGiftMessage"  → GiftMessage { user, gift{name}, repeatCount, groupId }
                      ├─ method == "WebcastLikeMessage"  → 点赞
                      ├─ method == "WebcastMemberMessage"→ 进场
                      └─ method == "WebcastRoomUserSeqMessage" → 在线人数
```

**连接前需要三样东西**：

1. `room_id` —— 从 `https://live.douyin.com/<短号>` 页面里正则抓 `roomId`
2. `ttwid` —— 访问页面时 Set-Cookie 返回
3. `signature` —— JS 算的（`webmssdk.js` 里的 `frontierSign`，输入是 `X-MS-STUB`）

**心跳**：每 10 秒发一帧 `payloadType='hb'`。服务端回 `needAck=true` 时要回 `payloadType='ack'`。

**注意**：用 `requests` 直接打 `/webcast/im/fetch/` 是不行的——服务端会校验 `Sec-WebSocket-Key`、`Origin`，还会看 TLS 指纹。

## 六、合规风险（这一段比技术部分重要）

这类玩法的雷集中在三件事同时出现：

1. **送礼换次数**
2. **排行榜刺激攀比**
3. **有奖 / 猜中给东西**

三件凑齐，很容易被判定为**诱导打赏**，情节严重的会被认定具有**赌博**性质。平台侧还有：

- 互动玩法（尤其涉礼物、涉随机、涉竞猜）通常要求**报备**，绕过报备轻则限流重则封号
- 未成年人打赏退款
- 公会合约里的独家条款、结算周期

**我的建议**：

- 不要做「猜中有奖」的实物/现金奖励，把奖励停留在**榜单位置、称号、徽章**这类虚拟荣誉
- 不设「付费必中」的机制，付费只能买**更多次数**，不能买**确定结果**
- 开播前自己去抖音**规则中心 / 直播开放平台**把互动玩法相关条款读一遍，别信任何二手总结（包括我这段）

⚠️ 我不是法律或平台规则的专业人士，以上是风险提示，不是合规结论。真要规模化做，找懂平台规则的人过一遍。

## 七、结论

**技术不难，生意不轻。**

- 技术上：拿弹幕有现成轮子，算分自己写一晚上，画面是网页。**两周内能做出能播的版本。**
- 生意上：工具本身没有壁垒（几百块就有成品卖），壁垒在**选词库、节奏、话术、投流**。这是内容生意，不是软件生意。

所以路线应该是：**先用最小成本验证「有人愿意为猜词送礼」这个假设**，再决定要不要投入做产品。

具体怎么验证，见 `02-操作手册.md` 的阶段划分。
