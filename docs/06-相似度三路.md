# 06 · 相似度是怎么算的（三路信号）

主播最常被问的一句话是「凭什么『衣领』82 分，『衣巾』76 分，『苹果』18 分？」

这个问题其实是三种完全不同的直觉混在一起。把它们拆开，才谈得上调参。

---

## 一、三种相似度，对应三种观众心理

| 类型 | 观众的原话 | 例子 | 本质 |
|---|---|---|---|
| **词义相近** | 「领口不就是衣襟边上那块吗」 | 领口 → 衣襟 | 概念上属于同一片语义区域 |
| **字面交集** | 「都有个『衣』字啊」 | 衣领 → 衣襟 | 两个词共用了汉字，看到就想试 |
| **读音相近** | 「我打的是谐音」 | 衣巾 → 衣襟 | 字形不同但听起来一样 |

这三种不是同一件事，也不能用一个模型统一处理：

- 词义要的是**世界知识**，只有向量模型和大模型有；
- 字面要的是**字形比对**，模型反而算不准（它对「襟」和「衣」的具体性区别无感）；
- 读音要的是**拼音**，模型压根不输入读音。

所以现在的实现是**三路信号并行计算，最后合成一个分**。

---

## 二、三路信号各自怎么算

### ① 词义：embedding + 本地大模型精排

```
余弦相似度 → 双锚点校准 → 0–100
```

- 默认模型 `quentinz/bge-small-zh-v1.5`（48MB，512 维），本地跑，零成本、约 20ms
- 校准：不相关词对的平均相似度映射到 8 分，人工标注的相关词对映射到 70 分
- 可选精排：本地 `qwen2.5:7b` 直接判分，比小模型的词义知识强得多
  （拿铁→咖啡 从 28.9 提到 85）

细节见 `05-语义引擎.md`。

### ② 字面：共享字，按稀有度加权

**先说结论：只共享一个字，给多少分，取决于这个字有多「泛」。**

`「子」「头」「口」`这种字几乎不携带信息，共享它说明不了什么；
`「襟」「扣」`这种字只出现在少数词里，共享它就有意义。

权重用 `1 / √(该字在本分类出现的词数)`，然后：

```
litRatio = Σ(命中字的权重) / Σ(答案每个字的权重)
lit      = 32 + 56 × litRatio        // 命中一个常见字 ≈ 40，全中 ≈ 88
```

实测：

| 猜测 | 答案 | 共享字 | litRatio | 字面分 |
|---|---|---|---:|---:|
| 裤腰 | 裤子 | 裤 | 1.000 | 88.0 |
| 衣领 | 衣襟 | 衣 | 0.320 | 49.9 |
| 平果 | 苹果 | 果 | 0.414 | 55.2 |
| 袖口 | 领口 | 口 | 0.500 | 60.0 |

> **包含关系单独处理**，不走这个公式。
> 「衣」是「衣襟」的子串，那是直接命中八成，用老的字频公式给 71.6；
> 「衣襟」是「旧衣襟」的子串，给 91。
> 包含比分字更确定，分数理应更高。

### ③ 读音：模糊拼音

先把汉字转成无声调拼音（预生成的表，见下文），再逐音节比对：

| 相似档位 | 条件 | 系数 | 例子 |
|---|---|---:|---|
| 完全同音 | 音节相同 | 1.00 | 巾 / 襟 `jin` |
| 模糊音等价 | 归一后相同 | 0.86 | 领 / 林 `ling→lin`、山 / 三 `shan→san` |
| 同发音部位 | 韵母同、声母同组 | 0.62 | 襟 / 钦 `j` vs `q` |
| 韵母同、声母远 | — | 0.32 | 襟 / 拎 `j` vs `l` |
| 不像 | 其余 | 0 | 巾 / 领 |

模糊音只做母语者真的会混的那几组，不做无节制合并：

- 平翘舌：`zh/ch/sh → z/c/s`
- 前后鼻音：`ing→in`、`eng→en`、`ang→an`、`iang→ian`、`uang→uan`
- 鼻边音：`n → l`
- 声母同部位：`j/q/x`、`z/c/s`、`b/p/m/f`、`d/t`、`g/k/h`、`n/l`

**整词比对时会有长度折扣**：短的那个在长的上面找最佳连续窗口，命中的部分再乘
`0.6 + 0.4 × (短/长)`。所以「巾」对「衣襟」整词只有 0.80，但它确实完整命中了「襟」，
所以另外保留一个不打折的 `wordSimRaw = 1.0` 用于保底判断。

## 三、合成：为什么不是简单加权平均

加权平均有个致命问题：三个信号都「中等偏上」的词，会莫名其妙超过「词义极近」的词。

现在的规则写了三条，都能当场向观众解释：

```
1. 词义 和 字面 取较大者
2. 读音作为「结构加成」叠加，不做主导：
     完全同音  → 字面分 + 26
     模糊同音  → 字面分 + 16
     近音      → 字面分 + 6
3. 保底：词义和字面都不像，但有一段音节被完全听对 → 至少 62 分
```

**为什么读音只加成不主导**：如果同音字直接给到 90，「巾」猜「襟」就等于猜中了，
游戏立刻失去难度。所以读音再像，也压在真近义之下。

**为什么要保底**：观众打「衣巾」的时候，他是真的听成「衣巾」了，
不是胡说。这时候系统给 16 分，观众会觉得「这 AI 是聋的」。给 62 才符合他的直觉。

### 实测三个信号的贡献

用 39 组人工标注跑 `node tools/bench.mjs`：

| 类型 | 条数 | 平均误差 | 最大误差 |
|---|---:|---:|---:|
| 语义相近 | 24 | 8.5 | 43.0 |
| **共享字** | 5 | **2.8** | 4.0 |
| **同音/谐音** | 6 | **5.2** | 20.0 |
| 负样本 | 4 | 11.3 | 15.0 |

整体：平均绝对误差 **7.6**，误差超过 25 分的「荒谬」只有 **3/39**，与人工排序的秩相关 **0.793**。

共享字和读音这两类的误差（2.8 / 5.2）明显低于纯语义（8.5）——
因为它们本来就是确定性计算，不依赖模型的知识。

## 四、拼音表是怎么来的（为什么不用 npm 依赖）

`lib/pinyin-table.json` 是 `node tools/gen-pinyin.mjs` 预生成的：

- 覆盖基本汉字区 20992 字，只有 136 个生僻字查不到读音
- 407 个不重复音节，用「2 个 ASCII 字符编码音节下标」压缩，文件 **47.6 KB**
- 运行时**零依赖**，不装 `pinyin-pro` 也能跑

`pinyin-pro` 只是 `devDependency`，只在重新生成表时才需要：

```bash
npm install          # 装 pinyin-pro
npm run gen:pinyin   # 重新生成 lib/pinyin-table.json
```

> 只有改了生成逻辑、或者想换拼音库时才需要重跑。日常运行完全不需要 `node_modules`。

## 五、已知的失败案例（换更大模型之前的硬上限）

| 猜测 | 答案 | 期望 | 实测 | 原因 |
|---|---|---:|---:|---|
| 苹果 | 手机 | 40 | 83 | 「苹果」是品牌还是水果，模型选了品牌 |
| 兔子 | 小狗 | 50 | 82 | 都归类成「小动物」，判得偏近 |
| 围巾 | 衣领 | 58 | 30 | 位置相邻但功能不同，模型判远了 |
| 山 | 三 | 30 | 30 | ✅ 同音但无关，被正确压住 |

前三类属于**词义本身有歧义**，换更大的模型只能缓解。
根治要把「本局答案的语境」一起喂给模型，那是下一步。

## 六、想调参时改哪里

| 想改什么 | 改哪里 | 注意 |
|---|---|---|
| 共享字整体高低 | `lib/score.mjs` → `literalScore` 的 `32 + 56 × ratio` | 上限 88，别高过包含关系 |
| 泛字惩罚力度 | `1 / Math.sqrt(df)` 换成 `1 / df` 会更狠 | 太狠会让「衣领」这种明显接近的词掉下来 |
| 同音加成 | `lib/score.mjs` → `structS` 的 `+26 / +16 / +6` | 改大之前先想清楚：会不会让谐音变成白送分 |
| 读音保底分 | `score()` 里的 `if (phoRaw >= 92 && s < 62)` | 62 是「明显有分但不接近答案」的位置 |
| 模糊音范围 | `lib/phonetic.mjs` → `canon()` 和 `GROUP` | 加太多会让不相干的词互相污染 |
| 换 embedding / 精排模型 | `.env` 的 `EMBED_MODEL` / `JUDGE_MODEL` | 见 `05-语义引擎.md` |
