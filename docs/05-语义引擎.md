# 语义引擎：从「字面对照表」到「三层打分」

这份文档记录关联度算法从 v0 到 v1 的改造过程、实测数据，以及踩过的坑。

---

## 一、v0 为什么必须换

v0 是「人工语义图谱 + 字面兜底」：我手写了一张 158 个词的分类/簇对照表，词落在表里就按簇距离给分，落在表外就只能逐字比对。

问题不在公式，在**覆盖面**。模拟观众的高频猜测里只有 **38.6%** 在表内：

```
衣服 上衣 布 衣 装 扣 领 襟 袋 线 针 缝 鞋 袜 领口 棉 麻 丝 毛 皮 绸 缎 绒
纱布 牛仔布 制服 校服 睡衣 泳装 旗袍 唐装 和服 汽车 飞机 房子
```

这些恰恰是观众最爱打的词。结果就是这些词全部落到「逐字比对」分支，共用一个字都没有时直接判 8 分：

| 答案 | 观众猜 | v0 得分 | 人的直觉 |
|---|---|---:|---|
| 咖啡 | 拿铁 | 9.2 | 应该 85 |
| 咖啡 | 奶茶 | 87.0 | 应该 60 |
| 衣襟 | 领口 | 9.5 | 应该 80，比袖口近得多 |
| 衣襟 | 袖口 | 84.1 | 应该 66 |
| 小狗 | 猫 | 9.0 | 应该 70 |
| 手机 | 充电宝 | 8.4 | 应该 75 |

「领口 9.5、袖口 84.1」这一组最能说明问题：**算法根本没有语言知识，只有一张表。**

## 二、v1 的三层结构

```
观众猜词
   │
   ├─ ① 字面包含关系 ──────────→ 字频公式（94 − 3.2×字频）
   │   「襟」比「衣」具体，这件事 embedding 分不出来，只有字面层能判
   │
   ├─ ② embedding 余弦 ────────→ 双锚点校准 → 0–100
   │   任意词都能算，覆盖词表外的词
   │
   ├─ ③ LLM 精排（可选）───────→ 直接问本地 8B 模型「这两个词多相关」
   │   最接近人的直觉，带缓存与超时预算
   │
   └─ 兜底：模型不可用 ────────→ 整体退回 v0 图谱
```

三条原则：

1. **字面包含优先**。猜「襟」和猜「衣」对答案「衣襟」的含义完全不同，embedding 给出的相似度可能一样，必须由字频公式区分。
2. **embedding 主导分数，图谱只做 ±2~4 分的先验修正**。手工簇的分数量级是拍出来的（同簇固定 87 起步），不能压过真实语义。
3. **任何一层挂掉都不能中断游戏**。模型没装、Ollama 没起、请求超时，统统退回上一层，页面上的分数照常出。

---

## 三、校准：为什么必须做

原始余弦对中文短词是压扁的：无关词 0.26–0.40，明显相关 0.50–0.62。直接 ×100 会得到「拿铁 38 分、苹果 47 分」这种更荒谬的结果。

用**双锚点**映射：

| 锚点 | 含义 | 本次实测 | 映射到 |
|---|---|---|---|
| `μU` | 跨分类随机词对的平均相似度 | 0.3223 | 8 分 |
| `μR` | 30 组已知相关词对的中位数 | 0.5525 | 70 分 |

两锚点之间线性插值（8→70），超过 `μR` 后斜率减半（70→92），再往上收敛到 97。这样做的原因：

- 如果 `μR` 直接映射到 90，所有同域词都会挤在 95+，榜单失去区分度（第一版就是这么翻车的：袖口 95.8、衬衫 92.7）。
- 高价区留白，只有「前襟 vs 衣襟」这类真近义才能上 90。

锚点参数落盘在 `data/embed-cache.json` 的 `calib` 里，**同一批词每次跑出的分数完全一致**，不会因为重启而抖动。

## 四、精排层：为什么需要大模型

小 embedding 模型对短词的知识非常有限。实测 bge-small-zh（24M 参数）：

```
拿铁   vs 咖啡   0.38      ← 比「苹果 vs 咖啡 0.47」还低
充电宝 vs 手机   0.35
```

这不是校准能救的，是模型不认识这些词。换成 8B 对话模型直接问，同一批词拿到 85 / 75，和人的判断一致。

代价与对策：

| 问题 | 对策 |
|---|---|
| 首次调用要加载模型，约 20 秒 | 启动时后台空跑一次预热，不阻塞服务 |
| 单批 6 对约 1.5 秒 | 批量判定，一次请求打分多对 |
| 直播等不起 | **先出 embedding 分，精排结果回来后再改榜单**（见下） |
| 重复猜同一个词 | 按「答案\|猜测」存盘缓存，同一局内命中率很高 |
| 模型太慢 / 挂了 | 超时预算 + 一次重试，失败就保留 embedding 分 |

### 先给分、后复核

这是服务端的实现方式，也是这一层能用在直播里的关键：

```js
// 观众发弹幕 → 立刻用 embedding 出分（毫秒级），榜单马上刷出来
const { score: s, hit } = await score(word, answer, { judge: false })
state.board.push(entry)
broadcast()

// 后台问大模型，回来如果差得多，就改这一条并重新广播
if (!hit) refineScore(entry, word, answer)
```

观众看到的效果是**分数自己往上走了一点**，比转圈等 1.5 秒好得多。实测：

```
衣领  81.2 → 70（已复核）
布扣  52.7 → 70（已复核）
```

## 五、实测对比

`node tools/bench.mjs` 对 26 组人工标注词对做 A/B：

| 指标 | v0 图谱 | v1 语义（embedding） | v1 + 精排 |
|---|---:|---:|---:|
| 平均绝对误差 | 31.9 | 20.9 | **8.7** |
| 荒谬对数（误差 > 25） | 13 / 26 | 8 / 26 | **3 / 26** |
| 与人工排序的秩相关 | 0.041 | 0.212 | **0.721** |

v0 的秩相关 0.041 意味着它的排序基本等于随机——这也解释了为什么真实观众会觉得「这分数是乱给的」。

完整逐条对比见 `data/report-bench.md`（由 `--out` 生成，不入库）。

### 仍然会错的三种情况

| 案例 | 期望 | 实测 | 原因 |
|---|---:|---:|---|
| 苹果 → 手机 | 40 | 83 | 单看词面，模型分不清是水果还是品牌 |
| 兔子 → 小狗 | 50 | 82 | 都算「常见小动物」，模型判得偏近 |
| 围巾 → 衣领 | 58 | 30 | 位置相邻但功能不同，模型判得偏远 |

这三类都属于**词义本身有歧义**，靠换更大模型只能缓解、不能根治。真要做得更准，需要把「本局答案属于哪个语境」一起喂给模型，那是下一步的事。

## 六、配置

所有配置走环境变量或 `.env`（`.env` 已在 `.gitignore`，代码里不出现任何密钥）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `EMBED_PROVIDER` | `auto` | `ollama` / `openai` / `off` |
| `EMBED_MODEL` | `bge-m3` | 推荐 `bge-m3`；轻量可用 `quentinz/bge-small-zh-v1.5` |
| `EMBED_BASE_URL` | `http://127.0.0.1:11434` | OpenAI 兼容服务就填它的 `/v1` 地址 |
| `EMBED_API_KEY` | 空 | 只有云端 provider 需要 |
| `JUDGE` | `auto` | `on` / `off` / `auto` |
| `JUDGE_MODEL` | 自动挑 | 优先 qwen2.5:7b 一类的本地中文模型 |
| `JUDGE_TIMEOUT_MS` | `25000` | 首次要等模型加载，别设太小 |
| `JUDGE_BATCH` | `6` | 一次判几对，越大越快但单次更久 |

启动方式：

```bash
ollama pull bge-m3                      # 或用更小的 bge-small-zh
cp .env.example .env                    # 按需改模型名
node server.mjs
```

启动日志会打印当前引擎和校准参数：

```
✓ embedding: ollama / bge-m3  (1024 维，缓存 158 条)
✓ 校准: 不相关基准 0.3223 · 相关基准 0.5525 · σ 0.0602
```

想对比两套引擎：`node tools/bench.mjs --no-judge`（只 embedding）与不加参数（含精排）。

## 七、换更大的模型

| 模型 | 体积 | 适合 |
|---|---|---|
| `quentinz/bge-small-zh-v1.5` | 48 MB | 笔记本/老机器，快，但短词知识有限 |
| `shaw/dmeta-embedding-zh` | ~400 MB | 中文专用，性价比更好 |
| `bge-m3` | 1.2 GB | 中文最好，支持长文本，跑得动就选它 |

换模型后 `data/embed-cache.json` 会自动作废重算（缓存里记了模型名），校准参数也会重新生成，不需要手工清理。

> 实测提醒：`bge-m3` 在这台机器上下载失败过（分片全是 66 字节的空文件），换小模型立刻就通了。如果拉取卡住，先看 `~/.ollama/models/blobs` 里有没有正常增长的 `-partial` 文件。

## 八、性能账

| 项目 | 耗时 | 说明 |
|---|---|---|
| 词表预热（158 词） | 首次约 3 秒，之后走缓存 | 启动时一次 |
| 单个新词的 embedding | 约 20–60 ms | 词表外的词才需要 |
| 一批 6 对的精排 | 约 1.5 秒 | 后台执行，不阻塞出分 |
| 精排首次加载模型 | 约 20 秒 | 启动时预热掉 |

一局 90 秒、约 60–80 个不同的词，精排摊下来平均每秒不到一个批次，CPU 占用可控。真正吃资源的是同时开着的 OBS + 浏览器，不是这一层。
