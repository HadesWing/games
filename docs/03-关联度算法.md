# 03 · 关联度算法（图谱版）

> **这一版已经是历史设计。** 现在实际跑的是 `docs/05-语义引擎.md` 里的三层结构：
> 字面包含 → embedding → LLM 精排。本文的图谱打分退居为「字面包含层的公式来源」和「模型不可用时的兜底」。
> 保留这份文档是为了说明**当初为什么要这么设计**，以及参数是怎么从截图里反推出来的。

主播最容易被观众问倒的一句话是：「凭什么『衣襟』86 分，『衬衫』只有 62 分？」

答不上来，观众就不信这个游戏了。所以**分数的可解释性比准确度更重要**。

---

## 一、从截图数据反推出的三个约束

拿截图的真实分数反推，能得出算法必须满足的三条：

### 约束 1：具体性优先于字面重合

| 猜测 | 分数 |
|---|---|
| 襟 | 89.8 |
| 衣 | 64.1 |

两个字都在答案里，分差 25 分。区别在于**「襟」在服饰词汇里只出现在 2 个词里，「衣」出现在几十个词里**。

→ **越罕见的字越值钱。**

### 约束 2：不是严格的同义判定

| 猜测 | 分数 |
|---|---|
| 布扣 | 84.6 |
| 纽扣 | 77.2 |

「纽扣」和「布扣」在语义上几乎是同一个东西，但分差 7 分。说明它不是一个「同义词查询」，而是**在某个语义空间里的连续位置**。

→ **不能用同义词表，要用距离。**

### 约束 3：同分类的无关词要落在 55–70

「衬衫」62.8、「领结」59.3、「棉毛衫」59.0——都是服饰，但都不是答案。

→ **同分类保底 55 分左右，不能太低**，否则榜单会很难看（一大片 10 分）。

---

## 二、当前实现（`lib/score.mjs`）

零依赖、确定性（同词永远同分）。按优先级三层：

```
① 猜测包含完整答案        → 91 分（不算猜中）
② 猜测是答案的子串        → 94 - 3.2 × (该字在本分类出现的词数)
③ 双方都在语义图谱里      → 同簇 87~82、同分类 61~48、跨分类 13
④ 至少一方不在图谱里      → 看共有字的罕见程度，46~80
```

第 ② 条是核心。举例，答案是「衣襟」：

| 猜测 | 该字在服饰词里的出现次数 | 分数 |
|---|---|---|
| 襟 | 2 | 87.6 |
| 衣 | 7 | 65.2 |

出现次数越多 → 字越泛 → 分越低。这一条用一个简单的统计量就复现了「襟 89.8 > 衣 64.1」的观感。

### 实测效果

答案「衣襟」时的输出（`node -e` 可复现，见 README）：

```
衣襟儿   91.0   superset        ← 包含答案，但不给过
襟       87.6   subset          ← 罕见字，高分
衣领     86.9   same-cluster    ← 同簇
衣角     83.3   same-cluster
襟花     72.5   shared-char     ← 图谱外，但共享罕见字
衣       65.2   subset          ← 常见字，被压下来
扣子     59.3   same-category
衬衫     55.0   same-category
领结     51.7   same-category
苹果     14.2   cross-category
不存在的词  3.0  unknown
```

和截图的分布形状基本一致。

## 三、当前实现的局限

必须清楚知道它做不了什么，否则会误判「算法已经好了」。

| 做不到 | 例子 | 后果 |
|---|---|---|
| 跨类隐喻 | 答案「丝绸」猜「水」 | 会给个位数，但人觉得「滑」有联系 |
| 多义词消歧 | 「领」= 衣领 / 领导 | 只看字面，不会按语境取义 |
| 网络梗 / 流行语 | 答案「雪糕」猜「刺客」 | 完全抓不到 |
| 图谱外的词 | 任何新词 | 只能靠共有字硬凑，经常离谱 |
| 词库规模 | 155 个词 | 换一题换几次就重复了 |

**结论：当前版本够用来验证玩法，不够用来正式开播。** 正式播之前必须升级。

## 四、升级路线 1：词向量（推荐先做这个）

成本最低、延迟最低、完全离线。

### 选型

| 模型 | 体积 | 维度 | 说明 |
|---|---|---|---|
| `BAAI/bge-small-zh-v1.5` | ~95 MB | 512 | 推荐，小、快、中文好 |
| `thenlper/gte-small-zh` | ~120 MB | 512 | 备选 |
| 腾讯词向量 | ~6 GB | 200 | 词级，词表大但太重 |

### 在 Node 里直接跑（不用 Python）

```bash
npm i @xenova/transformers
```

```js
import { pipeline } from '@xenova/transformers'

const embed = await pipeline('feature-extraction', 'Xenova/bge-small-zh-v1.5')

async function vec(text) {
  const out = await embed(text, { pooling: 'mean', normalize: true })
  return out.data // Float32Array，已归一化
}

const cos = (a, b) => a.reduce((s, v, i) => s + v * b[i], 0)

const vA = await vec('衣襟')
const vG = await vec('衣领')
console.log(cos(vA, vG)) // 0.8x
```

### 关键：余弦值要**标定**，不能直接 ×100

余弦相似度集中在 0.5–0.95 之间，直接乘 100 会全都变成 50–95 分，没有区分度。

标定方法：

1. 手工造 100 组「答案 + 猜测」，人工打 0–100 分
2. 算它们的余弦值
3. 拟合一条分段线性映射（或直接用分位数映射）

```js
// 经验值，需用自己的数据重标
function calibrate(cos) {
  if (cos >= 0.92) return 96
  if (cos >= 0.85) return 80 + (cos - 0.85) / 0.07 * 16
  if (cos >= 0.70) return 55 + (cos - 0.70) / 0.15 * 25
  if (cos >= 0.50) return 20 + (cos - 0.50) / 0.20 * 35
  return Math.max(3, cos * 40)
}
```

**这一步别省。** 不标定的结果就是「什么词都 70 多分」，观众立刻失去兴趣。

### 缺点

- 只能比「词和词像不像」，做不了「在服饰语境下像不像」
- 生僻词、网络新词不在训练语料里，向量质量差

## 五、升级路线 2：大模型打分（准确但要花钱）

### Prompt（可直接用）

```
你在主持一个中文猜词游戏。本局答案是「{answer}」，类别是「{category}」。
观众猜了「{guess}」。

请给出两者的关联度（0-100 的整数），评分标准：
- 完全相同：100
- 同义 / 同一物的另一种叫法：85-95
- 同类下的不同具体物品：70-84
- 同一大类下的不同部件：55-69
- 只在大类上沾边：35-54
- 几乎无关：0-34

只输出一个数字，不要任何解释。
```

参数：**temperature = 0**，max_tokens = 4。

### 必须做缓存

猜词这个场景，**重复率高得离谱**。「扣子」「纽扣」「衣领」这种词，每局都会被不同的人猜十几遍。

```js
const cache = new Map() // key: `${answer}|${guess}`
const key = `${answer}|${guess}`
if (cache.has(key)) return cache.get(key)
```

缓存命中率实测通常 70–85%，**成本能砍掉 4/5**。

### 成本估算

按每天 5000 条不重复猜测、用 flash 级别模型（约 ¥0.001/千 token）：

```
5000 × 100 token × ¥0.000001 ≈ ¥0.5 / 天
```

**大概几毛钱到几块钱一天。** 不贵。

### 缺点

- 有网络延迟（100–800ms），高峰期榜单会「慢半拍」
- 模型有随机性，同词两次可能不同分 → 温度 0 + 缓存必须双保险
- 断网就废了

## 六、推荐架构：三层混合

```
猜测词进来
   ↓
① 内存缓存命中？ → 直接返回（命中率 70%+，延迟 0）
   ↓ 未命中
② embedding 算余弦 → 粗排（本地，5ms）
   ↓
③ 分数落在「模棱两可区」（58-78）？ 
   ├─ 是 → 调大模型精排（远程，300ms）
   └─ 否 → 直接用 embedding 分数
   ↓
写入缓存 → 返回
```

为什么这么设计：

- 极高分（>85）和极低分（<50）**几乎不会判错**，不值得花大模型的钱
- 只有中间地带需要「语境判断」，这才是大模型的用武之地
- 缓存覆盖了绝大部分请求

预期效果：**准确度接近纯大模型，成本接近纯 embedding，延迟接近本地。**

---

## 七、落地顺序建议

不要一次全上。按这个顺序，每步都能独立验证：

1. **先扩词库**（最快见效）——155 词扩到 800+，标注好分类和簇。这一步纯体力活，但直接解决「换几题就重复」
2. **接 embedding**——替换 `score()` 里第 ③ ④ 层，用余弦 + 标定映射
3. **加缓存 + LLM 精排**——只在中间区调用
4. **做 A/B**——同一批测试词，两种算法各跑一遍，人工看哪个更像人

第 1 步做完就能明显感觉不一样，而且不花钱。**建议今天就先干这个。**
